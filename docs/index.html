The thesis

Four times, a change that looked right by one measurement was wrong by another.

The most interesting part of this project is the corrections: an eager-loading strategy that was right in theory and wrong at this data volume, a cache that made single requests 3× faster and concurrent throughput 40% worse, a 44 ms stall that turned out not to exist in production, and four database indexes added on a prediction and dropped once the usage statistics disagreed.

What follows is the full record, in the order it happened. Every number below was measured against a fixed baseline on the same machine — the ones that made things worse are kept in as carefully as the ones that worked, because the reversals are the part that took skill.

ACT I

The system

An ad auction is a ranking problem with a budget attached and a hard latency ceiling. Everything downstream comes from that shape.

Every POST /auction carries a user_id. The service has to decide, in milliseconds, which of ~23,000 campaigns is allowed to be shown to that specific person, rank the survivors, pick one, charge the advertiser, and log enough context that the decision can be audited later. There is no real traffic, so the project generates its own: 2,000,000 simulated users, 5,000 advertisers, 40 interests, and a traffic simulator that produces realistic impression/click/conversion chains.

Three separable stages, on purpose

The auction is deliberately split into filter → score → pick winner, with a fourth side-effecting step kept apart from the rest. That separation is an ML-readiness decision made early: score_campaign is the one function a trained model would eventually replace, and it can be swapped without touching eligibility rules or auction mechanics.

Two decisions that shaped everything after

Weighted random instead of argmax. The highest-scoring campaign does not always win; odds are proportional to score. A deterministic winner would mean a broad campaign with weaker targeting could never compete at all. Real auctions and recommendation systems both preserve room for exploration. Verified statistically over 1,000 trials rather than asserting one exact outcome, because the behaviour is intentionally probabilistic.

A baseline score of 1.0, always. Scoring pure interest overlap would give an untargeted campaign a score of zero — and under weighted-random selection, zero means mathematically excluded forever. Broad campaigns are legitimate and common, so every eligible campaign carries a floor.

Ad-tech detail

A “no fill” — zero eligible campaigns for this user — returns 204 No Content, not 404. The request was valid and the auction ran correctly; the inventory was empty. Treating a normal business outcome as a client error is the kind of thing that poisons dashboards later.

The impression stores a snapshot instead of a set of pointers

Each Impression row stores the user's age, country, device and interests as they were at decision time, rather than referencing the live user row. That looked like redundant denormalisation early on. It became load-bearing much later, when interest weights started changing from click behaviour — without the snapshot, historical records would have silently drifted to describe decisions that were never actually made.

ACT II

First contact with load

A single auction request took 1.75 seconds. The first fix was obvious, but finding the best fix required more measurement.

EXPLAIN ANALYZE isolated timing Locust

The N+1, and why another approach performed better than the recommended fix

get_campaign_candidates returned 2,263 campaigns with no eager loading. The Python loop then touched campaign.targeting and targeting.interests on each one — and every single access silently fired its own query. One query became roughly 4,500.

The textbook fix is selectinload for many-to-many collections, specifically because it avoids the row duplication a join introduces. It took the request from 1.75 s to ~0.4 s. That was a real 4× win, and stopping there would have been defensible.

Measuring one layer deeper showed that joinedload performed better at this data volume. The plain query alone was ~54 ms. Adding joinedload(targeting) barely moved it, ~41 ms. Adding selectinload(interests) jumped it to ~343 ms — while EXPLAIN ANALYZE showed the underlying data was cheap to fetch, ~13 ms via an equivalent plain join. The overhead came from selectinload's own mechanism: a single query carrying a literal WHERE targeting_id IN (...) list of 2,263 individual UUID parameters.

ACT III

The cache that made it worse

Redis made a single request 3× faster and cut concurrent throughput by 40%. Twice, for two entirely different reasons.

Caching the eligible-campaign computation is the obvious move: the candidate list barely changes between one request and the next, yet it was being recomputed from scratch every time. Measured on sequential single requests, it was a clean win — 0.518 s cold, 0.167 s warm, roughly 3×.

Then it went under load.

Configuration50 users100 users
No cache3,100 ms · 7.8 rps11,000 ms · 7.2 rps
With cache7,800 ms · 4.8 rps15,000 ms · 4.8 rps

Regression 1 — the stampede, caught with redis-cli MONITOR

MONITOR streams every command Redis receives, with timestamps. Over a 25-second test with a 5-second TTL, the expected number of SETEX calls is about 5 — one per expiry. The actual count was 69, arriving in bursts of 10, then 14, then 18, then 27, each burst lining up exactly with a TTL expiry and each one worse than the last as Locust ramped concurrency.

That is a cache stampede: the instant the entry expires, every concurrent request misses simultaneously and independently redoes the same expensive query. The backend now takes a recurring burst of identical redundant load. It performed worse than running without caching.

Four industry-standard fixes were weighed: single-flight locking, stale-while-revalidate, probabilistic early expiration, and scheduled background refresh. Stale-while-revalidate won because it was philosophically consistent with a decision the project had already made — bounded spent staleness had already been accepted as “budget pacing”. Serving a few-seconds-stale candidate list is the same trade. It also lets every request continue without waiting.

Redis TTL alone reports whether an entry exists rather than how old it is, so a computed_at stamp went inside the payload, with two thresholds instead of one: fresh under 5 s, usable-but-refresh-in-background to 30 s, genuine miss past that.

The gap in the first attempt

The lock initially guarded only the background-refresh path. The cold start had no lock at all — so the opening moment of every load test still stampeded. MONITOR showed it precisely: 13 total SETEX, down from 69, but 10 of those 13 clustered in the first second. The steady-state fix left the identical bug at t=0 and made it harder to see.

Regression 2 — the GIL, and why throughput refused to move

With the stampede gone, throughput remained flat. The clue was arithmetic: 1 / 0.18 s ≈ 5.5 rps, and the measurement was 4.8. The server was achieving essentially serial throughput — getting almost no benefit from concurrency whatsoever.

Measured directly, deserialising one cache hit cost 88.5 ms of pure-Python CPU: json.loads on a 668 KB payload (2.7 ms) plus the construction of 9,344 SQLAlchemy ORM objects (85.8 ms) — 2,257 campaigns, 2,257 targeting rows, 4,830 interests. Each instance pays for SQLAlchemy's instrumentation: change-tracking history, relationship sync, a per-object state container.

The actual lesson

Python's GIL permits one thread to execute bytecode at a time, but releases during I/O. Before caching, a large part of each request was spent waiting on Postgres with the lock released, so other requests progressed. After caching, that wait was replaced by 88 ms of pure Python that holds the lock continuously and blocks every other in-flight request. The optimisation traded the one property that made concurrency work for the one that looks better in a single-request benchmark.

The fix, validated before it was built

The lightweight-data-shape option had been considered and rejected earlier, on the grounds that keeping real ORM objects meant no changes to matches_targeting, score_campaign, or the test suite. The evidence reversed that decision.

Rather than implement and hope, a microbenchmark built the same 2,257 candidates both ways: real ORM objects versus plain @dataclass(slots=True) equivalents exposing the same attribute names. 80.9 ms → 10.7 ms, a 7.6× speedup, confirming the cost confirming that SQLAlchemy's instrumentation caused the overhead.

The expected test rewrite turned out to be unnecessary. matches_targeting and score_campaign rely only on the attributes of what they receive; they do not read attributes. Duck typing meant a test constructing a real AudienceTargeting and production handing over a CandidateTargeting were indistinguishable. All 18 tests passed with zero changes.

ACT IV

Finding the real ceiling

Before chasing the next bottleneck: the benchmark itself was wrong, and had been for two sections.

py-spy locustfile_fast pg_stat_activity per-core CPU sampling

Correction: the load generator capped the throughput

Locust's default wait_time = between(1, 3) inserts about 2 s of think time between a simulated user's requests. That caps how much load a given user count can ever offer, regardless of how fast the server is: max offered rps ≈ users / (think_time + response_time). At 50 users that ceiling is about 25 rps — and the celebrated 22.07 rps from the previous section sits almost exactly on it.

The test rig reached its limit before the server did. Re-measured with think time removed:

RPS falling from 50 to 150 users while latency climbs linearly is the real saturation signature. True single-process capacity was ~36–39 rps, not 22. The previous conclusion remained valid, while the headroom estimate built on it was invalid.

py-spy, and a red herring worth keeping

Sampling the live server under real load showed _deserialize_candidates consuming 51.1% of CPU samples — every request was still rebuilding ~9,300 objects that were identical for every request served in the same cache window. Memoising the deserialised list per process, keyed by a freshness stamp, dropped that share to 0.4%.

The same investigation surfaced a 43 ms stall inside record_win that looked like a major find. It was chased, isolated, and then disproved: running the identical probe inside a Linux container on the same Docker network gave 1.93 ms against 43.96 ms on the Windows host. Docker Desktop's port-forwarder caused the stall, and production bypasses that development-only path. The correct action was to preserve the code and document the finding.

Eight workers, and why 4.4× is the right answer

Python's GIL is per process, so the way to use the other cores is more processes. The hazard was worked out on paper first: each worker builds its own engine, so connection pool settings multiply. 50 connections per worker × 8 workers = 400 against a Postgres max_connections of 100. The pool was resized to 10 per worker before anything was launched, and the rejection was reproduced deliberately to confirm the math.

Then it broke at 2,400 users and revealed two bugs

Bisecting for the exact failure threshold was considered and explicitly rejected because it would identify where the failure began without explaining why, and a specific mechanism was already suspected. A controlled comparison at fixed load was the more informative move and revealed both bugs.

Bug one: the default thread limiter

Rather than trusting memory, the limit was confirmed from the installed source: 

$ grep -n "CapacityLimiter(40)" .venv/.../anyio/_backends/_asyncio.py
3162:            limiter = CapacityLimiter(40)

anyio's default thread limiter is hard-coded to 40, independent of CPU count and unchanged by this project's settings. FastAPI runs every sync path function through it. So up to 40 requests per worker could be mid-flight, each holding a real OS thread and competing for the GIL, queued behind a pool that could serve only 10. The fix aligned the two numbers exactly.

Bug two: found while verifying the first fix

At 600 users the server stalled completely. Zero requests completed in 48 seconds. Postgres sat pinned at exactly 80.0 of 80 connections idle-in-transaction, static, not fluctuating. Worker CPU was 3.4%.

The answer came from the server's own log rather than more theorising: a real sqlalchemy.exc.TimeoutError: QueuePool limit of size 6 overflow 4 reached. The background cache-refresh thread ran on a raw threading.Thread and bypassed anyio, so it was invisible to the limiter that had just been sized to match the pool exactly. It consumed connections the limiter treated as reserved.

Fixed by giving the background refresh its own isolated single-connection pool, and shortening pool_timeout from 30 s to 3 s so genuine overload fails fast and self-recovers instead of hanging. Result at the same 600 users: 4,776 requests in 40 s, 30.49% failures — but all failing quickly, with the server recovering in 5–10 s rather than requiring a restart.

The capacity cliff, measured

With both bugs fixed and the mechanisms understood, bisection became the right tool for finding the exact capacity threshold.

ACT V

The write path, audited before adding Kafka

The plan was to move writes off the request path. Profiling first found a revenue bug instead.

Kafka was next on the roadmap, justified by “the write is slow”. Before building infrastructure on that premise, the premise got measured. Decomposing one auction request into phases:

Correction — a finding the project already had

The 44 ms stall was initially re-diagnosed as TCP Nagle / delayed-ACK. The project's own performance playbook had already tested and rejected that exact hypothesis in an earlier session, and correctly attributed it to Docker Desktop's Windows port-forwarder. Re-confirmed: 43 ms on the host, 1.93 ms inside a Linux container. The code was deliberately left unchanged because production bypasses that Windows port-forwarding path. Rewriting code to dodge a laptop artifact would have added permanent complexity to work around a local environment.

The bug that was real: 90% of charges silently disappearing

campaign.spent += COST_PER_WIN reads the value into Python, adds, and writes it back. Three operations, and another worker can land between them. Two workers winning the same campaign concurrently both read the same starting value, both write the same result, and one charge vanishes. Under READ COMMITTED, Postgres will not stop this.

Passing tests do not prove a race is fixed, so it was proven with a forced collision: 10 threads × 5 wins on one shared campaign, synchronised on a barrier so they all start together.

ImplementationImpressionsChargedOwedLost

Under forced collision the old code served 50 impressions and billed for five. This becomes the dominant outcome once several concurrent requests win the same popular campaign, which is exactly the traffic pattern the project's own load tests generate.

+ db.execute(
+     update(Campaign)
+     .where(Campaign.id == campaign.id)
+     .values(spent=Campaign.spent + COST_PER_WIN)   # one atomic, row-locked statement

The same audit removed three redundant queries: record_win was scoring a re-fetched ORM object, triggering two lazy loads for data the caller already held in memory, then refreshing a row it had just written. Seven SQL statements per win became three.

What this did to the Kafka plan

Re-running the capacity sweep after these fixes: at 300 users, where the system previously collapsed to 194 rps with 11.92% failures, it now ran at 1,084 rps with zero failures — and the failure cliff did not reappear anywhere through 1,600 users.

The honest reading, recorded at the time: two variables changed — the code and the measurement environment. The clean single-variable proof is the race test above, not this sweep. The original throughput justification for Kafka was now gone. Kafka was still built deliberately for decoupling and durability, and it was no longer described as a throughput fix.

ACT VI

Events, and a system that learns

Clicks stop writing to Postgres. A separate process writes them. Then the clicks start changing what gets shown.

Why the partition key is the click's own id

Kafka guarantees ordering only within a partition, and messages sharing a key always land on the same partition. That is the only lever available for controlling order. A click event and any conversion referencing it are both keyed on the click's id — which guarantees a consumer always sees the click before the conversion that depends on it.

At-least-once, and what makes it safe

Offsets are committed manually, only after a message is actually written to Postgres. The default — commit as soon as poll() returns — would advance the offset before the write, so a crash in between loses the event permanently. Committing afterwards means a crash causes redelivery instead of loss.

That is only safe because redelivery is harmless: each row's primary key is the event's own client-generated id, so a replay hits a duplicate-key IntegrityError — a reliable “already handled” signal rather than a reason to write twice. Proven by republishing an identical event and confirming the row count stayed at exactly one.

The bug that hung everything

The first end-to-end run produced zero consumer output while the container reported healthy. Producing worked; every consumer-group operation hung, including the command-line tools. The answer was in docker logs, repeating every 250 ms forever: Sent auto-creation request for Set(__consumer_offsets).

Kafka's internal offsets topic defaults to a replication factor of 3. One broker cannot satisfy that setting, so topic creation never completes and every operation depending on a consumer group's coordinator waits forever on it. Three *_REPLICATION_FACTOR: 1 overrides fixed it. The symptom concealed the cause; the broker's own log revealed it.

The eventual-consistency window, observed rather than asserted

The click endpoint now returns 201 with a usable id before the row exists anywhere in Postgres. Querying immediately after the response returned zero rows, every time, until the consumer caught up moments later. That gap is the entire trade the design makes, and it was verified directly rather than described.

Then the clicks start changing the auction

Every interest starts at a flat weight of 1.0 for every user. On a click, the consumer credits the clicked campaign's full targeted interest set (+1.0) and decays every other interest that user holds (×0.95). Crediting the whole set, rather than only the overlap that made the campaign eligible, is what lets a click reveal a genuinely new interest instead of only reinforcing known ones — the difference between preference learning and preference confirmation.

Closing the loop

Writing weights alone has no effect. score_campaign had to read them — summing a user's real per-interest weights instead of counting matched interests. Eligibility was deliberately left alone: weight shifts the odds among already-eligible campaigns, it never decides whether a campaign is eligible at all.

Verified as an outcome shift rather than a code change. Against the same 192 eligible campaigns for the same real user, 3,000 trials each:

Of 158 targeted eligible campaigns, 112 scored differently — showing that the effect extends well beyond a crafted edge case. The work also surfaced a real bug: Impression.score was an Integer column, too narrow for weighted sums that are no longer whole numbers.

ACT VII

Instrumentation, and a metric that lied

The library's own documented one-liner produced plausible, real-looking numbers that were wrong on every scrape.

Prometheus pulls metrics from the app through scrapes. Adding prometheus-fastapi-instrumentator gave automatic request counts, latency histograms and status codes, plus custom counters for auction wins, no-fills, suspicious clicks and idempotent replays.

The exposition looked fine. It was checked anyway, because this app runs uvicorn --workers 4 and every metric object lives in whichever process created it. Scraping the same counter six times in a row:

The fix is prometheus_client's multiprocess mode: with PROMETHEUS_MULTIPROC_DIR set, every metric writes to a per-PID file, and /metrics builds a fresh registry per request to merge them. The registry must be rebuilt per scrape rather than once at startup, since its entire job is reading the current state of every worker's file.

After the fix, forty requests produced exactly 40.0 on every repeated scrape — cross-checked against the independently-computed http_requests_total, which also read 40.

Dashboards provisioned as files

The Grafana datasource and an eight-panel dashboard are provisioned from files in the repo. Anything created through the UI lives only in the container's internal database. Recreating the container deletes that work, and version control has no record that it existed. The datasource uid is pinned, because Grafana otherwise generates a random one per install and every panel's reference breaks on a fresh machine.

Verification, because dashboards fail silently

A panel with a subtly wrong metric name renders as an empty chart that looks like “nothing is happening right now”. So every panel's query was executed through Grafana's own datasource proxy and checked for a non-empty result. Two came back empty — and both queries were correct; the events they describe simply hadn't happened since the last restart. Proven by deliberately generating the 401s and the idempotency replay they were waiting for.

One genuine bug did surface: a labelled counter doesn't appear in the metrics output at all until first incremented, so that panel read “No data” instead of 0 on a fresh process. Fixed with or vector(0).

ACT VIII

Hardening, by threat model

Endpoint protection varies because some callers can keep a secret and others cannot.

The tempting move is “add auth to everything”. Working out why that is wrong is most of the value here. Who actually calls each endpoint determines what can protect it:

Endpoint groupReal callerCan hold a secret?Protection
Advertiser writesAn advertiser's backendYes — server-sideAPI key + ownership checks
Auction & trackingEnd-user browsersNo — readable by anyoneRate limiting, fraud heuristics
Analytics readsThe dashboardNot meaningfullyOpen — aggregate data only

A key embedded in browser JavaScript is exposed to every user, so it cannot protect a tracking pixel and only creates a false sense of security. That is why the split exists.

The hole that authentication actually closed

POST /campaigns took an advertiser_id in the request body and trusted it. Any caller could create campaigns that spent against someone else's account. The fix is structural rather than additive: the field was deleted entirely, eliminating the spoofing target, and ownership is derived from the authenticated key.

A test performs the actual attack — attacker's key, victim's id in the body — and asserts the created campaign does not belong to the victim.

Targeting needed a second, genuinely different check. Authentication identifies the caller; ownership validation determines whether this campaign belongs to that caller. A mismatch returns 404, not 403 — a 403 would confirm the campaign exists and let an authenticated advertiser enumerate competitors' ids by probing.

Why SHA-256 here, when passwords need bcrypt

A password is short, human-chosen, and drawn from a small realistic space, so password hashing is deliberately slow to make each guess expensive. An API key from secrets.token_urlsafe(32) is 256 bits of uniform randomness — there is no dictionary and brute force is infeasible however fast the hash runs. A slow hash adds no security benefit here.

And a fast deterministic hash buys something bcrypt structurally cannot: the same key always hashes to the same value, so authentication is one indexed lookup instead of loading every advertiser and testing each salted hash in turn.

Rate limiting, and the one command that makes it safe

A fixed-window counter over Redis INCR — atomic, server-side, returning the new value. Doing this as read-add-write in Python would be the exact lost-update shape fixed in Act V. Third time that same lesson appeared in this project.

EXPIRE is applied only when the counter equals 1, on the request that created the key. Re-applying it every request would slide the expiry forward continuously, silently turning the limit into “N requests ever” rather than “N per window”.

Known weakness, acceptedboundary bursting — 100 requests at 09:59.9 and 100 at 10:00.1 are both legal

Idempotency has to begin with the client

The Kafka consumer already deduplicates redelivery of the same message. It cannot deduplicate an HTTP retry, and the reason is worth tracing: record_click generates a fresh uuid4() per call. A client whose connection drops and retries produces a genuinely different click id, publishes a genuinely different event, and the consumer — correctly, by its own rules — writes both.

One real click, two recorded clicks. On an ad platform that is double-counted billing. The information that these two events are “the same operation” exists only on the client, which is why an Idempotency-Key header is the only layer that can fix it.

Click fraud: flagging, not blocking

A human who genuinely saw an ad cannot click it in 50 ms. Since the impression row is already loaded for the 404 check, elapsed time is free to compute. Measured: a scripted click at 0.058 s was flagged; a click after a human-plausible pause at 1.271 s was not.

It deliberately flags rather than blocks. A single naive heuristic will have false positives, and a false positive here means refusing a real user's real click — silently under-reporting a campaign's performance and under-billing. Plenty of legitimate traffic is fast: a pre-rendered page, a mis-tap, an accessibility tool, an aggressive prefetcher.

A schema lesson this surfaced

The consumer reads the new field as event.get("suspicious", False), not event["suspicious"]. Events produced before the heuristic existed are still sitting in the Kafka topic and are still replayable — the whole point of a durable log. A consumer that assumed every message matched the newest producer's schema would crash on its own history.

ACT IX

The surface

A dashboard asks different questions than a REST resource API answers.

Every existing endpoint was resource-shaped: GET /campaigns returns campaign rows. A dashboard needs aggregate answers — total impressions, best campaigns, click-through rate. Building those from resource endpoints would mean the browser fetching 23,268 campaigns and 699,813 impressions to compute a number Postgres produces in one query.

So three aggregate endpoints exist specifically because a UI asks different questions. The summary computes all eight totals as scalar subqueries inside a single SELECT, so the header costs one round trip rather than eight. The top-campaigns query aggregates first and joins the small results, because joining raw impressions to clicks and grouping afterwards would multiply every impression row by that campaign's click rows before collapsing them again.

Two problems revealed by the rendered page

The interest-weight chart needs a baseline around 1.0. Every interest starts at exactly 1.0 and the largest real drift after live traffic is about 1.000012. A bar chart anchored at zero renders all ten bars at effectively full width — visually identical, information content zero. The chart scales by drift from 1.0 instead, with the baseline stated in the panel so the axis accurately reflects the variation.

The budget column needed a number alongside the bar. Real spend sits around 4% of budget. A bar communicates “how close to the cap” well at 60%, but at 4% it renders as an invisible nub and fails to communicate the spend. The underlying data and component were correct, while the visual presentation was ineffective.

Proof of live polling beyond a screenshot

With the page open and untouched, 25 real auctions were generated against the API from outside the browser. The impressions counter moved from 699,057 to 699,082 — exactly +25, with no page reload. That is the difference between a dashboard that reads live state and one showing a cached first render.

Grafana and this dashboard both exist deliberately. Grafana is the operational view — request rates, latency percentiles, error classes; it answers “is the system healthy?”. The React dashboard is the business view — spend, CTR, campaign performance, learned weights; it answers “is the advertising working?”. Merging them would produce one dashboard serving neither audience.

The stable candidate count ruled out increased data volume; the machine was busier, now running Prometheus, Grafana, a Vite dev server and a Kafka consumer. Attributing that to code would have been wrong, and checking the candidate count is what ruled it out.

The reversal

Four foreign-key indexes had been added on the prediction that the new analytics queries would need them. Measurement showed the dashboard's GROUP BY correctly ignores an index — it reads every row regardless — while the indexes cost ~0.60 ms on every impression insert, the hottest write in the system.

The first instinct was to keep them anyway, justified by foreign-key enforcement. Then pg_stat_user_indexes was consulted, and it disagreed:

The only two indexes costing the auction hot path had been used exactly once each — by the queries written to prove they could be used. The foreign-key argument was real but hypothetical: this project has no deletion paths for users or campaigns, and it has no per-campaign drill-down endpoints that would use them. Insert cost after dropping them: 1.61 ms → 1.247 ms.

The process lesson, which is the bigger one

One step added the indexes on a prediction. The next step's first draft kept them on a plausible-sounding argument. The idx_scan measurement produced the right answer. The usage statistics existed the entire time and would have skipped the whole round trip.

An index is infrastructure with a recurring cost on every write, so “we might need it later” requires stronger evidence, just like adding a message queue does.

The rate limiter distorted the load test

Rate limiting is 100 requests per 10 s per IP, and every request from Locust or the traffic simulator originates from one machine — so the entire load generator shares one bucket. A capacity sweep at 300 users would be almost entirely 429s, measuring the rate limiter rather than the system. The simulator, which calls raise_for_status(), crashed outright on the first one.

A protection mechanism working correctly can still invalidate your measurement tools. The limit was made configurable rather than hardcoded, so a load test can raise it without editing code.

The measurement rules that came out of it

  • Measure the dimension you actually care about. For a server, measure throughput and tail latency under concurrent load instead of the speed of one request in isolation.
  • Check the rig before trusting the result. Two sections of conclusions were built on a number capped by the load generator rather than the server.
  • Boundaries absent from production can distort measurements. A Windows/Linux VM edge, a port-forwarder, a load generator sharing the server's CPU.
  • Prove a race fix with forced collision. Passing tests alone can miss the race; a thread barrier exposes it.
  • Empty and broken look identical. Trigger the expected event to distinguish an empty dashboard panel, Prometheus series, or consumer from a broken one.
  • Prefer the number over the argument. idx_scan, redis-cli MONITOR, py-spy, EXPLAIN ANALYZE — each one ended a debate that reasoning alone had gotten wrong.

Open work, tracked explicitly

  • Horizontal scaling. Flagged since the first load tests and still unimplemented. It will likely move the bottleneck onto the single Postgres, which is the interesting part.
  • The ML preference model. Genuinely blocked: it needs real click history, and there are 54 clicks.
  • Signed impression tokens. The hardening work raised the cost of faking a click and made it visible, while the attack path remains open.
  • The new throughput ceiling. ~1,080–1,200 rps across every load level from 100 to 1,600 users, with tail latency rather than failures as the overload signal. The limiting resource remains unidentified because the investigation chose measurement over guessing.
